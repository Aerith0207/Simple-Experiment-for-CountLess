# Count-Less 复现实验设计与结果

## 1. 复现目标与范围

本实验在 Python 软件环境中复现 Count-Less 的核心更新机制，目标是回答两个问题：

1. Pyramid 计数结构与 Minimum Update 是否能提高计数精度？
2. 它们在什么负载和 Flow Size 下退化，退化可能来自什么机制？

实验尚未覆盖真实 CAIDA 流量、攻击混合流量、完整 FCM/Elastic 基线与硬件资源评估，因此应定位为“核心机制的软件级复现与探索”。

## 2. 算法与消融设计

| 算法 | 数据结构 | 更新方式 | 对照作用 |
| --- | --- | --- | --- |
| CM | 标准 Count-Min | 全部更新 | 传统基线 |
| CM-CU | 标准 Count-Min | Conservative Update | 验证保守更新收益 |
| CL-CM | Pyramid | 全层更新 | 隔离 Pyramid 结构的作用 |
| CL-CU | Pyramid | 全局 CU | 软件中的理想化精度参考 |
| CL-MU | Pyramid | Minimum Update | Count-Less 核心方案 |

核心消融关系：

- `CM → CL-CM`：观察结构改变。
- `CL-CM → CL-MU`：观察 Minimum Update 的收益。
- `CL-CU → CL-MU`：观察单向流水线友好的 MU 相对理想 CU 的精度代价。

## 3. 实验链条

### 3.1 基础正确性与哈希随机性

初始配置为 100,000 packets、5,000 flows、8 KB，Zipf 参数为 1.2/2.0/3.0，种子为 42–46。单元测试覆盖更新、查询和饱和处理。

最初的线性哈希与连续 Flow ID 发生了强映射规律：在相同 Zipf=2.0 与 8 KB 下，CL-MU ARE 随种子从 0.149 到 2.447 大幅波动。更换为 SplitMix64 后，第一层占用位置稳定在 3062–3090，后续正式实验统一使用五个随机种子。

结论边界：SplitMix64 显著缓解了已观察的映射异常，但这不等于证明哈希完全随机，也不等于严格复现论文的哈希实现。

### 3.2 Zipf 流量下的基础精度

五种子平均 ARE：

| 算法 | Zipf 1.2 | Zipf 2.0 | Zipf 3.0 |
| --- | ---: | ---: | ---: |
| CM | 9.552 | 5.435 | 5.156 |
| CM-CU | 5.915 | 3.069 | 2.780 |
| CL-CM | 2.014 | 1.097 | 1.014 |
| CL-CU | 1.296 | 0.674 | 0.620 |
| CL-MU | 1.456 | 0.752 | 0.688 |

在当前配置中，排序稳定为：

`CL-CU < CL-MU < CL-CM < CM-CU < CM`

这表明 Pyramid + MU 有效，但 MU 相对理想 CU 仍有精度代价。Zipf 越大 ARE 反而越低，与论文的部分趋势不同；当前只能确认流大小组成、流量构造、规模与内存压力均不同，尚未完成单一因素归因。

### 3.3 内存敏感性

固定 Zipf=2.0、100,000 packets 和 5,000 flows：

| 内存 | CL-MU ARE | CL-MU Mouse FSR | CL-CU/MU ARE 差值 |
| --- | ---: | ---: | ---: |
| 8 KB | 0.7521 | 41.54% | 0.0784 |
| 16 KB | 0.2465 | 76.39% | 0.0293 |
| 32 KB | 0.0664 | 93.36% | 0.0072 |
| 64 KB | 0.0152 | 98.46% | 0.0011 |

内存增加时 CL-MU 精度明显改善，并在绝对 ARE 上逐步接近 CL-CU。“碰撞减少导致 MU/CU 决策更接近”是合理解释，但尚未通过更新次数分解直接验证。

### 3.4 固定内存的整体负载压力测试

配置：8 KB，Flow 数为 1,000/2,000/5,000/10,000/20,000，流大小组成固定为 80% 的 1 包流、15% 的 10 包流、4% 的 100 包流和 1% 的 1000 包流。

| Flow 数 | CL-CU ARE | CL-MU ARE |
| ---: | ---: | ---: |
| 1,000 | 0.061 | 0.068 |
| 2,000 | 0.304 | 0.329 |
| 5,000 | 1.774 | 1.885 |
| 10,000 | 5.965 | 6.298 |
| 20,000 | 18.105 | 19.161 |

CL-MU Mouse FSR 从 95.31% 降到 3.96%，Elephant FSR 从 100% 降到 90.6%。这不是单独的 Cardinality 实验：Flow 数增加时，总包数也从 16,300 增加到 326,000。

### 3.5 Flow Size 分组

CL-MU FSR：

| Flow 数 | 1-packet | 10-packet | 100-packet |
| ---: | ---: | ---: | ---: |
| 1,000 | 94.50% | 98.40% | 100.00% |
| 2,000 | 80.35% | 92.87% | 100.00% |
| 5,000 | 37.67% | 55.41% | 99.60% |
| 10,000 | 11.63% | 14.96% | 95.05% |
| 20,000 | 1.40% | 1.44% | 64.63% |

FSR 判据为严格的 `|估计-真值|/真值 < 0.1`。因此 1-packet 和 10-packet Flow 都不能容忍任何整数高估，而 100-packet Flow 可容忍最多 9 个包的高估。

20,000 Flows 时，CL-MU 分组 ARE 为 23.528、2.223 和 0.135。单包流占 80%，对总体 ARE 的贡献约为 `0.8 × 23.528 = 18.822`，约占总体 19.161 的 98.2%。

结论：总体 ARE 的急剧上升不代表所有 Flow Size 同速退化；极小流占比高时会主导相对误差。

### 3.6 100-packet Flow 上的 CU/MU 差距

20,000 Flows 时，100-packet Flow 的 Final FSR：

- CL-CU：91.70%
- CL-MU：64.63%
- 差距：27.08 个百分点（按未四舍五入的原始值计算）

这说明平均 ARE 接近并不意味着各 Flow Size 的精度也接近。

### 3.7 Cross-layer Rescue 机制诊断

100-packet Flow、8 KB、20,000 Flows、五种子均值：

| 指标 | CL-CU | CL-MU |
| --- | ---: | ---: |
| Layer 1 FSR | 87.08% | 42.10% |
| Layer 2 FSR | 74.20% | 47.88% |
| Layer 3 FSR | 38.03% | 16.48% |
| Rescue Rate | 4.63% | 22.53% |
| Final FSR | 91.70% | 64.63% |
| ARE | 0.0589 | 0.1346 |

CL-MU 从 L1 的 42.10% 提升到最终 64.63%，说明高层确实挽救了部分低层失败。但 CL-MU 的 Rescue Rate 较高不等于挽救机制更优：条件概率 `P(被挽救 | L1 失败)` 约为 38.9%，CL-CU 约为 35.8%，两者接近。更准确的解读是 CL-MU 有更多 Flow 需要高层挽救。

最明显的差异在第一层。MU 从低到高顺序更新，第一层只要未饱和就会更新；CU 则基于三层的全局最小值决定是否更新第一层。“MU 累积额外无关更新”是当前机制假设，尚未完成因果验证。

## 4. 其他值得保留的观察

### 碰撞不等于饱和

20,000 Flows 时，第一层有共享映射的 Flow 比例约为 98.62%，但真正饱和的计数器仅约 4.26%。碰撞会引入高估噪声，但不一定使 8-bit 计数器达到 255。饱和还可能由 1000-packet Elephant Flow 自身造成。

### 总体优势不代表每一类流都优势

20,000 Flows 时 Elephant FSR：CM-CU 为 98.4%，CL-CU 为 93.6%，CL-MU 为 90.6%。一种可能解释是 CM-CU 在每层使用完整位宽并执行全局保守更新，但尚需更受控的流大小和高层碰撞实验才能确认。

## 5. 当前证据与未解问题

| 已观察现象 | 当前证据 | 未解问题 |
| --- | --- | --- |
| CL-MU 比多个基础方案误差更低 | 多 Zipf、五种子、内存敏感性 | 真实流量与更多基线下是否成立 |
| 高负载下 Mouse FSR 严重下降 | 固定内存压力测试 | Flow 数与包数各自的影响 |
| 单包流主导总体 ARE | Flow Size 分组 | 下游安全任务是否也由其主导 |
| 100-packet Flow 上 CU/MU 差距显著 | 20,000 Flows 分组 | 哪些额外更新造成差距 |
| 高层可挽救部分低层失败 | Rescue 分析 | 哪些 Flow 可被挽救 |
| MU 各层 FSR 低于 CU | 逐层计数器分析 | 额外更新、碰撞与层间状态各占多少 |

## 6. 下一步 Update Noise Decomposition

对每个包到达前的同一份 Sketch 状态，同时计算 CU 和 MU 的更新集：

`U_extra = U_MU - U_CU`

按 Layer、Flow Size 和负载统计额外写入，再检查它与最终 FSR/ARE 的关联。不能直接比较两个已经运行很久、内部状态不同的 Sketch，并把计数器差值解释为 MU 噪声。额外更新次数也只是机制证据；若要证明它造成最终精度差距，还需要受控的反事实实验。
